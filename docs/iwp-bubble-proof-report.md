# IWP-to-Bubble Relabeling: First Proof Report

**Status:** Feasibility proof passed; production validation not yet complete  
**Date:** 2026-09-18  
**Project:** `pioneer-api`

## Executive conclusion

The core methodology is mechanically feasible.

A deterministic pipeline can:

1. Read an InSpec Classic `.iwp` file without losing its UTF-16LE encoding, BOM, long-line structure, or CRLF endings.
2. Extract named source features and canonical coordinates.
3. Normalize source units into millimetres.
4. Render a deterministic reference image from the source geometry.
5. Register or apply an image-space transform.
6. Match mismatched bubble numbers to source features by geometry and leader endpoint rather than by label equality or array order.
7. Write a new IWP in which only the matched `(Name "...")` values are replaced.

This report proves the mechanics with a deterministic six-feature fixture. It does **not** yet prove that the system works on a real customer bubbled PDF or with a production image model.

## Public reference basis

Micro-Vu’s public validation package contains `Validation 1.iwp`, `Validation 2.iwp`, and IQ/OQ validation PDFs. The OQ document describes running the two programs and comparing exported measurement data against expected results.[^1]

Micro-Vu’s official IWP editing guidance confirms that IWP programs are UTF-16LE text with CRLF line endings and very long lines. It also documents editing command forms such as `AutoRptPrn` in Notepad++.[^2]

These references establish the file-format behavior and provide realistic public IWP syntax. They do not provide a real bubbled engineering drawing paired with the IWP source.

## Deterministic six-feature fixture

The fixture contains six source point features with arbitrary IWP names and inch coordinates:

| Source name | Source coordinate | Bubble number |
| --- | ---: | ---: |
| `A17` | `(0.4, 0.4)` in | `705` |
| `A18` | `(1.2, 0.4)` in | `102` |
| `A19` | `(2.0, 0.4)` in | `991` |
| `A20` | `(0.4, 1.2)` in | `314` |
| `A21` | `(1.2, 1.2)` in | `808` |
| `A22` | `(2.0, 1.2)` in | `127` |

The bubble numbers intentionally do not match the IWP names. Bubble observations are shuffled before matching. Each bubble has a center offset from the source feature and a leader endpoint at the transformed feature anchor.

The test then:

- converts inches to millimetres;
- renders the canonical and transformed source geometry;
- generates a bubbled SVG with offset callouts;
- applies a deterministic affine transform with scale, translation, and Y-axis inversion;
- matches bubbles by leader endpoint proximity;
- derives the six source-to-bubble mappings;
- rewrites the six IWP names;
- verifies UTF-16LE/BOM/CRLF preservation.

Expected derived mappings:

```text
A17 → 705
A18 → 102
A19 → 991
A20 → 314
A21 → 808
A22 → 127
```

## Evidence

The deterministic proof has **5 passing tests, 24 assertions, and a successful TypeScript build**. The live Gemini observation evaluation adds two adapter tests, for a current total of **7 passing tests, 26 assertions**.

The proof covers:

- encoding preservation;
- source-name replacement;
- named-record and group extraction;
- unit normalization;
- affine coordinate transformation;
- offset leader endpoints;
- shuffled observation order;
- one-to-one matching;
- duplicate and ambiguity rejection;
- deterministic SVG source/bubble/match/output layers;
- structured Gemini output validation and normalized-to-pixel conversion.

The interactive review artifact is generated by `fixture:visualize` and includes the decoded IWP, five visual layers, transform data, mapping data, and a derived source-to-bubble evidence table.

## Live Gemini evaluation on the synthetic fixture

The first real image-model call now runs through AI SDK with Google Gemini 3.6 Flash. It evaluated the generated `03-bubbled-input.png`, which contains six deliberately mismatched bubbles and offset leader lines.

| Measure | Result |
| --- | ---: |
| Bubble observations expected | 6 |
| Bubble observations returned | 6 |
| Missing bubble numbers | 0 |
| Unexpected bubble numbers | 0 |
| Maximum leader-endpoint error | 2.56 px in the 1200×800 SVG canvas |
| Model tokens | 3,206 |
| Evaluation | Passed |

Gemini returned all six labels—`705`, `102`, `991`, `314`, `808`, and `127`—with structured normalized boxes, leader endpoints, and confidence values. The evaluator denormalized those observations into the SVG canvas coordinate space before comparing them with the fixture ground truth and invoking the IWP rewrite. This proves that the AI SDK/Google vision layer can feed the deterministic geometry matcher on this synthetic image.

The model input is rasterized PNG. SVG remains the inspectable, deterministic vector artifact and is not treated as the model's required vision input. The contracted application should replace the synthetic Google provider with Pioneer-authorized Claude access through GovCloud before real company data is processed.

This is **not** evidence of production accuracy: the image is clean, generated, known in advance, and contains only six point features. The result does establish a live model-backed observation path and a measurable evaluation harness.

## What has not yet been proven

### 1. No real customer-image evaluation yet

We have now evaluated a real multimodal model, but only against the generated fixture. We have not measured model behavior on a real bubbled PDF/image, manufacturing drawing clutter, low resolution, skew, occlusion, handwriting, or ambiguous leader lines.

### 2. Registration is known in the fixture

The fixture supplies the affine transform as test setup. It does not yet estimate the transform from the rendered IWP image and the bubbled PDF/image.

### 3. Renderer coverage is intentionally narrow

The current deterministic renderer faithfully supports point anchors for the proof. It does not yet fully decode and render every IWP feature type or every `Sys`/`PCS`/`Nom` transform. Lines, circles, arcs, ellipses, rectangles, slots, splines, and 3D projection still need implementation and comparison against the official validation programs.

### 4. No real bubbled source pair

The public Micro-Vu validation PDFs are validation reports, not the customer-style bubbled drawing/image required for the final proof. No real Pioneer sample has been used because clearance is still pending.

## Remaining work before a confident real-system claim

1. **Canonical IWP geometry layer**  
   Parse `Sys`, `PCS`, and `Nom` transforms, normalize all supported geometry to millimetres, and preserve feature provenance.

2. **Broader deterministic renderer**  
   Render lines, circles, arcs, ellipses, rectangles, slots, splines, and selected 3D features projected onto a chosen plane.

3. **Registration estimation**  
   Estimate affine or projective transforms from common anchors, fiducials, leader endpoints, or drawing bounds. Validate residuals and reject unstable registration.

4. **Real-image evaluation**
   Test the authorized production vision provider—Pioneer-authorized Claude through GovCloud—against at least one cleared bubbled PDF/image with known ground truth. Measure bubble detection accuracy, feature-match precision/recall, transform residuals, duplicate assignments, and rewrite fidelity.

5. **Audit and safety output**
   Persist source/image hashes, model/provider metadata, transform matrices, candidate matches, residuals, rejected matches, and the exact rewritten-name diff.

## Verdict

We can honestly claim:

> The IWP-to-bubble relabeling methodology is mechanically feasible and has passed a deterministic geometry/rewrite proof with intentionally mismatched labels, unit conversion, affine offsets, leader endpoints, shuffled observations, and one live Gemini structured-vision evaluation on the generated six-feature image.

We cannot yet claim:

> The system is validated against real bubbled manufacturing images, full IWP geometry, or real-world registration conditions.

The next decisive milestone is a cleared bubbled-image benchmark: render a corresponding IWP subset, rasterize the visual inputs, run the authorized Claude observation path, estimate registration, measure errors, and only then permit relabeling.
